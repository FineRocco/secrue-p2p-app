% Introduction Section
\subsection*{Introduction}

The programming language used for this project is Java, with Maven as the build tool, and the application was developed in Visual Studio and IntelliJ. The user interface was created with JavaFX, and SSL sockets were implemented to ensure secure communication between peers. Version control was managed through GitHub, facilitating collaboration among team members. 
\newline

The project is structured as follows:
\begin{itemize}
    \item \textbf{CentralServer} – a server that controls users information and generates the truststore.
    \item \textbf{SecureP2PMessagingApp} – the main class of the project where the interface is loaded.
    \item \textbf{P2PServer} – handles incoming messages from peers.
    \item \textbf{P2PClient} – allows users to send messages.
    
\end{itemize}

Additionally, four core entities are defined:
\begin{itemize}
    \item \textbf{Conversation} – manages message exchanges between users.
    \item \textbf{Message} – represents individual messages within conversations.
    \item \textbf{Share} - represents a share of user's key.
    \item \textbf{User} – identifies each user within the app.
\end{itemize}

% Features Section
\subsection*{Features}

The secure P2P messaging application offers the following features:
\begin{itemize}
    \item \textbf{Direct Messaging}: Enables users to initiate peer-to-peer communication by entering the recipient's username. If that username exists, the central server provides the recipient's IP address and port number to the sender. The sender can then send messages directly to the recipient.
    \item \textbf{Conversation Management and History}: Tracks all messages exchanged in the Conversations tab, with timestamps for chronological ordering retrieved from the cloud.
    \item \textbf{Message Searching}: Allows users to efficiently search for specific messages across all their conversations retrieved from the cloud.
    \item \textbf{Long-Term Storage of Messages}: Ensures messages are securely stored for extended periods using a distributed cloud storage system across three providers: \textbf{AWS S3}, \textbf{Firebase}, and \textbf{Azure}. This design guarantees privacy and security by encrypting messages before storage and employing Shamir's Secret Sharing algorithm for the secret keys. Redundancy is maintained to ensure availability, even in the event of a failure in one of the cloud providers.
\end{itemize}


% Security Section
\subsection*{{Security}}

Application security is implemented through SSL sockets, establishing encrypted channels that guard against interception and tampering. Key management is facilitated using individual keystores, generated by each peer, alongside a truststore, created exclusively by the central server and shared across all peers. The central server also generates its own keystore. Upon joining the network, each peer generates a certificate and imports it into the truststore, enabling secure handshakes between peers when exchanging messages.
\newline

The peer-to-peer communication leverages SSL sockets to ensure robust implementation of all primary security pillars:
\begin{itemize}
    \item \textbf{Confidentiality}: Ensures communication remains private by encrypting messages.
    \item \textbf{Integrity}: Prevents unauthorized tampering or alteration of messages.
    \item \textbf{Authenticity}: Validates the identity of peers through certificate-based verification.
\end{itemize}

The protocol used for secure communication is \textbf{TLSv1.2}, which is the default due to its compatibility with the majority of systems and JDK versions. The handshake process utilizes the cipher suite \textbf{TLS\_AES\_256\_GCM\_SHA384} for encryption algorithms, ensuring robust encryption of handshake messages. For certificate verification, the protocol employs the signature algorithm \textbf{rsa\_pss\_rsae\_sha256}, which provides a modern, secure approach to digital signatures. Additionally, the algorithm \textbf{SHA256withRSA}, provided by the \textit{BouncyCastle API}, is utilized for signature generation and verification, reinforcing the integrity and authenticity of the exchanged certificates.
\newline

In addition to securing communication, the system ensures \textbf{availability} by leveraging three cloud storage providers for storing encrypted messages. All data stored in the clouds is encrypted with the user's random key, ensuring its confidentiality. The key itself is securely stored in the clouds but divided into three shares using the \textbf{Shamir's Secret Sharing algorithm}. These shares are distributed among the clouds such that the key can be reconstructed using any two of the three shares. This redundancy ensures that even if one cloud fails, the system can reconstruct the key and access encrypted messages, maintaining high availability and reliability of the messaging platform

% Cloud Storage Section
\subsection*{Cloud Storage}

The system employs a distributed cloud storage architecture across three providers: \textbf{AWS S3}, \textbf{Firebase}, and \textbf{Azure}. This multi-cloud approach ensures that data is always accessible, even in the event of service disruption or failure in one of the providers.

The program is designed to retrieve data from the primary storage provider, \textbf{AWS S3}. If AWS S3 returns an error or becomes unavailable, the system seamlessly switches to \textbf{Firebase} to retrieve the data. In cases where both AWS S3 and Firebase are inaccessible, the system falls back to \textbf{Microsoft Azure} as the final retrieval point. This hierarchy ensures continuous availability of user data and minimizes service interruptions.

Each cloud storage provider organizes user data into structured folders for enhanced security and usability. Specifically:
\begin{itemize}
    \item \textbf{User Folder}: Each user has a dedicated folder, containing the following:
    \begin{itemize}
        \item \textbf{Encrypted Conversations}: All conversations associated with the user are stored in an encrypted format.
        \item \textbf{Shares Folder}: This folder contains the a share of the user's key.
        \item \textbf{Dictionary Folder}: This folder contains encrypted words from the user's messages.
    \end{itemize}
\end{itemize}

% Interface Section
\subsection*{Interface}

Upon initialization, the application prompts the user to enter their login credentials, specifically the username and port number (with the IP address defaulted to localhost). Following successful login, the main menu interface is displayed, presenting several navigation options in the form of buttons:
\begin{itemize}
    \item \textbf{Send Direct Message}: Form for recipient details (username, message).
    \item \textbf{Conversations}: Displays ongoing conversations and chat history with timestamps.
    \item \textbf{Search}: Searches for the word written in the text field in the all user's conversation history.
    \item \textbf{Exit}: Closes the application and terminates active connections.
\end{itemize}
\subsection*{Additional Information}
The exception handling mechanism is not implemented in the interface (e.g., same username, same port number, etc.).

% Conclusion Section
\subsubsection{Conclusion}
The project successfully implements a peer-to-peer messaging system, achieving a high level of decentralization. A central server is utilized solely for aggregating peer information, ensuring minimal central dependency. The platform incorporates SSL for secure communication, JavaFX for a responsive and user-friendly interface, and a well-structured application architecture to enable secure, direct, and organized messaging between users.

Cloud storage plays a crucial role in storing user conversation data and a portion of the key required to restore user sessions. However, it does not interfere with the peer-to-peer communication itself, preserving the decentralized nature of the system.

Regarding performance, the reconstruction or creation of the user's key occurs at the start of the session. While this process introduces a brief delay, it is essential to handle it on the main thread to ensure the user can immediately access the app with their key ready.
